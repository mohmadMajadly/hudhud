# ADR-0015: Legal posture and code provenance

- Status: Accepted as engineering policy. Owner decision 4 (2026-10-12): the owner confirmed the legal review. Nothing in this ADR is legal advice.
- Date: 2026-10-12
- Negotiation log items: A1, A2, R1 (06 header, §A)
- Related: [ADR-0001](0001-foundation-and-backends.md), [ADR-0011](0011-spawn-hygiene-and-binary-provenance.md), [ADR-0012](0012-security-defaults-and-trust.md)

## Context

The hudhud repository is private now and planned to become open source. Facts from 02 §9 (fetched 2026-10-12; the interpretation is UNVERIFIED):

- The TS Agent SDK is proprietary ("All rights reserved. Use is subject to the Legal Agreements"); the SDK's repository license points to the Commercial Terms of Service.
- The Python SDK code is MIT-licensed; its README still says use is governed by the Commercial Terms.
- The Claude Code legal and compliance page: preinstalling or running Claude Code in products requires agreeing to the Commercial Terms; the binary must not be modified; authentication methods must not be removed, disabled or restricted; customers may not pay for or resell Claude usage on behalf of end users; third-party developers may not offer claude.ai login or route requests through Free/Pro/Max credentials on behalf of users, nor collect, store or intermediate claude.ai credentials or session tokens; the Claude Code or Anthropic names and logos may not be part of a product, feature or company name.

## Decision

1. Protocol types are derived independently: from observed frames (05) and from the MIT Python SDK, with a NOTICE file for attribution. Nothing is copied from `sdk.d.ts`, `sdk.mjs` or other proprietary SDK files, including minified code.
2. The TS SDK is used only as an optional peer dependency, installed by the user under Anthropic's terms. hudhud never vendors, copies or redistributes it. It is also used as the CI differential oracle, from v1.1 ([ADR-0013](0013-testing-strategy.md)); the oracle is not distributed.
3. hudhud never bundles or redistributes the `claude` binary. It runs the user's installed, unmodified binary and does not modify it (R6).
4. hudhud never collects, stores or proxies OAuth tokens or claude.ai session tokens. hudhud has no login flow. The SDK features `getOAuthToken` and `claude_authenticate` (02 §9) are not implemented. Each end user authenticates with their own credentials through the harness.
5. The product name does not include "Claude Code" or "Anthropic"; describing hudhud plainly as driving Claude Code is acceptable. The owner reserves the npm names before the first publish (owner decision 3). Amendment (owner decision, 2026-10-16): reserved as the npm org `hudhudjs` (scope `@hudhudjs`) and the unscoped `hudhudjs`, after the scope `@hudhud` proved taken and npm refused `hudhud` as too similar to `hud-hud` ([ADR-0004](0004-packages-and-versioning.md)). Neither name includes "Claude Code" or "Anthropic".
6. No identity spoofing: the entrypoint stays at the honest default ([ADR-0001](0001-foundation-and-backends.md)).
7. Binary provenance checking is advisory ([ADR-0011](0011-spawn-hygiene-and-binary-provenance.md)).
8. A legal review is a precondition of open-sourcing; the owner confirmed it (owner decision 4). This policy stays binding regardless.
9. Third-party licenses of dependencies are tracked as part of the toolchain ([ADR-0017](0017-toolchain.md)); published packages carry provenance.
10. License (owner decision, 2026-10-14): hudhud is licensed under the Apache License 2.0 (`LICENSE` at the root and in every package, `"license": "Apache-2.0"` in every `package.json`). The root `NOTICE` ships in every package too (Apache-2.0 §4(d); W7-Z): each package lists it in `files`, its committed copy must equal the root file (since item 11: begin with it; `scripts/test/package-legal.test.ts`), and `pnpm check:tarball` requires a README, a LICENSE and a NOTICE in every tarball and compares the packed LICENSE and NOTICE with the root files byte for byte. Reasons: an explicit patent grant and patent-retaliation clause for a library other products build on, and a NOTICE file, which item 1 already requires. The owner may revisit MIT; relicensing future versions is possible while the owner is the sole copyright holder, so the choice must be settled before outside contributions are accepted. Published versions keep the license they were published under.
11. Third-party code inside a package (pre-release review R6-2, FX-D, 2026-10-17): the generated validators of `@hudhudjs/claude-code` (`src/generated/validators.gen.ts`, `src/protocol/generated/validators.gen.ts`, shipped as source and compiled into `dist`) inline Ajv's runtime helpers `ucs2length.js` and `equal.js` and the whole of fast-deep-equal, both MIT-licensed, whose notice must go with all copies or substantial portions. A package's `NOTICE` is therefore the root `NOTICE` followed by one section per bundled package, `--- <package> ---` and that package's own license text: `@hudhudjs/claude-code` carries Ajv's (Copyright (c) 2015-2021 Evgeny Poberezkin) and fast-deep-equal's (Copyright (c) 2017 Evgeny Poberezkin); every other package carries the root `NOTICE` unchanged, which says that a package lists its third-party code after it. `scripts/test/package-legal.test.ts` finds the bundled packages by esbuild's `// node_modules/<package>/` markers in a package's `src` and requires exactly those sections, each with the installed package's license text byte for byte; `pnpm check:tarball` requires every packed `NOTICE` to begin with the root file and to list every package a packed JavaScript or TypeScript file bundles. Searched for other bundled third-party code (2026-10-17): the core's generated validators bundle no runtime module; the addon's sources are hudhud's own (its import library is generated from `node-api-headers`' `node_api.def` at build time, no code of it ships); the static MSVC runtime is checklist item 3.7. Code that Ajv generates (the validator functions themselves) is the output of a tool, not a copy of Ajv; the notice is carried anyway, since the same files contain the helpers.
12. The static Microsoft C runtime in the Windows job addon (owner ruling, 2026-10-18; release checklist 3.7; research note of 2026-10-18 on the Visual Studio, Build Tools and Windows SDK license terms). `hudhud_win32_job.node` keeps `/MT`: it embeds object code of `libucrt.lib` (Windows SDK), `libvcruntime.lib` and `libcmt.lib` (MSVC toolset), in their Spectre-mitigated builds. Reasons for keeping it: `/MD` would not remove Microsoft object code (the CRT startup code is always linked statically, which is why CPython, a `/MD` build, carries the same notice), and the addon would import `vcruntime140.dll`, which Windows does not ship and `node.exe` (itself `/MT`) does not load, so containment would fall back to `'best-effort'` silently on machines without the Visual C++ Redistributable. An N-API addon that passes no CRT object (`FILE*`, heap pointers, locale) across its boundary is the case Microsoft's caution about `/MT` in a DLL accepts; node-gyp addons are `/MT` by default.
    - Licensing basis. The static UCRT is distributable by an explicit grant: the Windows SDK terms §2.a allow the object code of files on the SDK's REDIST list, which names the `.lib` files under `Windows Kits\10\Lib\<version>\ucrt\<arch>` "when built as part of your program", and allow `.lib` code only as linker output. The release `libvcruntime.lib` and `libcmt.lib` are not named on the Visual Studio Distributable List (it names `VC\redist` and the merge modules); their distribution rests on Microsoft's documentation, which marks only the debug static libraries "Not redistributable" and presents static linking as the way to avoid a runtime redistribution, and on universal practice (Node.js, ripgrep, uv and napi-rs packages ship static CRT code). This is an inference, not an explicit grant.
    - Notice. `@hudhudjs/win32-job-x64` (and `@hudhudjs/win32-job-arm64`, for when it ships) carries in its `NOTICE`, after the root text, a "Microsoft Distributable Code" section modelled on CPython's `PC/crtlicense.txt`: it scopes Apache-2.0 to the hudhud authors' code, names the Microsoft terms the embedded code is redistributed under, requires further distributors and end users to agree to terms that protect it at least as much, lists Microsoft's restrictions (notices, trademarks, Microsoft platforms only, no malicious use, no reverse engineering beyond what law permits), and states that hudhud is not affiliated with or endorsed by Microsoft; the package README says so in one line. Apache-2.0 §4(d) makes `NOTICE` informational, which fits: it does not change hudhud's license. `scripts/test/package-legal.test.ts` keeps both packages' sections equal and complete; `pnpm check:tarball` requires the section in the `NOTICE` of every package that ships a `.node` (`checkNativeNotice`). Item 11's "every other package carries the root NOTICE unchanged" now excludes these two.
    - Build of record. Release binaries are built only on GitHub-hosted runners by `addon-prebuild.yml` (the build of record, under the Visual Studio Enterprise installation of the runner image), never on a developer machine: the Build Tools license has no Distributable Code grant of its own, and a local release build would need a Visual Studio Community license. Local builds (`pnpm addon:stage`, `build.mjs --toolset-of-record`) are for development, tests and the independent reproduction of a CI record; they are never published. The release flow enforces it: a record comes from the CI artifact of phase 1, and `release.yml` publishes only the tarballs its own CI run built and checked (ADR-0014 amendment 12).
    - Obligations the owner accepts knowingly. The Visual Studio Enterprise 2022/2026, Visual Studio Community 2026 and Windows SDK terms require the distributor to "indemnify, defend, and hold harmless Microsoft from any claims, including attorneys' fees, related to the distribution or use of your applications, except to the extent that any claim is based solely on the Distributable Code"; no file can discharge this, and the owner accepts it. The terms also require the distributor to "require distributors and external end users to agree to terms that protect the Distributable Code at least as much"; npm has no click-through, so shipping the terms in `NOTICE` approximates it, as every precedent found does.
    - Not verified. No Microsoft text explicitly allows (or forbids) distributing the release `libcmt.lib` and `libvcruntime.lib` once linked (a 2022 Microsoft Q&A answer reported the gap in the documentation, with no answer since). GitHub's arrangement with Microsoft for the runner images' Visual Studio Enterprise licence is known only from a runner-images maintainer's statement (actions/runner-images issue 12945), not from a published agreement. Whether a Build Tools user without Community installed "holds" a Community licence; the Visual Studio 2026 Distributable List names Build Tools although the Build Tools licence has no Distributable Code section; whether "Win32" is a registered Microsoft trademark; whether a passive notice satisfies "require ... to agree".

## Alternatives considered

- Vendoring the TS SDK's types for convenience. Rejected: copying proprietary text is forbidden by 02 §9.
- Porting the Python SDK verbatim. Not chosen: MIT permits it with attribution, but hudhud's design differs materially ([ADR-0001](0001-foundation-and-backends.md)); ideas and observed behaviour are used, with a NOTICE.
- Redistributing the CLI binary with the library for convenience. Rejected: legal page and 02 §9 assessment.
- Offering a login helper that stores tokens. Rejected: prohibited credential handling.
- Skipping the legal review because nothing is copied. Rejected: owner rule R1 and the UNVERIFIED nature of the interpretation.

## Consequences

- hudhud cannot offer "managed" Claude access to end users; applications that embed it must meet Anthropic's terms themselves.
- Documentation must tell integrators that the harness must be installed and licensed by the end user or by them under the Commercial Terms.
- A NOTICE file and a dependency license audit are release requirements.
