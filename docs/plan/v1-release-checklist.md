Status: 2026-10-16, written by W7-T4 on main f2236d2 plus the W7-T4 branch; updated 2026-10-17 by W7-Z on the closer branch (all Wave 7 branches merged; items 1.10, 1.11 and 3.7 to 3.9 added); updated 2026-10-17 by FX-D of the pre-release review fixes on main 313b68b (states of 1.1, 1.4, 1.5, 1.7 and 3.3 from the CI runs; items 1.13, 1.14 (FX-A), 2.5, 3.10 to 3.12 and 4.10 to 4.12 added; 4.3, 4.4 and 4.8 restated). Updated 2026-10-18 by REL-1 (the release workflow, the private flags, the release runbook in §7, the owner rulings of 2026-10-18: first version 0.1.0, NOTICE holder "The hudhud authors", the repository public before the first publish with provenance on, `/MT` kept with a Microsoft notice). This is the list of every gate between the current tree and the first npm publish of `hudhudjs`, `@hudhudjs/core`, `@hudhudjs/claude-code`, `@hudhudjs/conformance` (added 2026-10-18, item 4.13) and `@hudhudjs/win32-job-x64`. Each gate says who acts, how it is verified and what state it is in today. A gate is closed only by its verification, never by a statement.

Who acts:

- **Owner**: only the repository owner can do it (npm account, GitHub settings, legal decisions). The agents prepare it, the owner does it.
- **Lead**: the lead dispatches, merges and decides.
- **Agent**: work an agent does on a branch, merged by the lead.

States: **done** (verified, evidence cited), **open** (work left), **owner** (waits for an owner action), **decision** (waits for a lead or owner ruling).

### Rollback and deprecation of a bad publish

- A version that was published can never be published again, even after an unpublish, so the remedy for a bad release is always a new version, never a re-tag.
- **Partial publish** (the publish job failed after some packages were published): do not delete or move the tag and do not unpublish. Fix the cause outside the code (registry, trusted publisher settings, environment) and use "Re-run failed jobs" on the same run: it publishes the same checked tarballs and skips every version already on the registry with the same bytes. If the artifact expired (7 days), "Re-run all jobs". If the cause is in the code, continue as for a bad release below; the packages already published stay, deprecated.
- **Bad release** (a defect or vulnerability in a published 0.1.0): **Owner** deprecates every package of the release at once so installs warn: `npm deprecate hudhudjs@0.1.0 "<reason>; use 0.1.1"`, and the same for `@hudhudjs/core`, `@hudhudjs/claude-code`, `@hudhudjs/conformance` and, if the addon is affected, `@hudhudjs/win32-job-x64`. Then fix, add a `patch` changeset, run the version PR and tag `v0.1.1`. When a previous good version exists, point `latest` back to it until the fix ships: `npm dist-tag add <package>@<good version> latest` for each package of the group. For a vulnerability, a GitHub security advisory follows the fix (SECURITY.md).
- **Addon defect**: the core pins the addon version exactly, so a fixed addon needs a new record (phase 1 with `release=0.1.1`), the table written from it and a library release whose core names it; deprecate `@hudhudjs/win32-job-x64@0.1.0` with the core versions that use it.
- **Unpublish** only for content that must not stay public (a leaked secret, malware, a legal demand), and only within npm's unpublish policy (generally 72 hours, no dependents): `npm unpublish <package>@<version>` by the owner; the version number is burnt; rotate any leaked secret first. Every other case is deprecate and fix.
