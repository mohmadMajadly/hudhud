## Context

Today the CLI runs as the user that runs hudhud. Whoever controls a Bash tool of the CLI therefore can, as that same user: signal or kill the host process, read its `/proc/<pid>/environ` (a ptrace read check that passes for the same uid while the host is dumpable), open every file the host can, and take over whatever the host talks to (Q2 §2.4 (c), [man] `kill(2)`, `proc(5)`, `ptrace(2)`). A sandboxed application whose control plane trusts what the host reports (permission outcomes, audit, billing) needs the agent unable to reach the host. The CLI and its tools always share a uid, because the CLI spawns its tools itself; no option of hudhud's changes that (Q2 §A.5).

Facts that shape the decision:

- Node's own `spawn({ uid, gid })` cannot do this safely (Q2 §2.1, §A.2): libuv calls `setgroups(0, NULL)` and ignores its failure, so a parent without `CAP_SETGID` leaves the child in the parent's supplementary groups; Node cannot set `no_new_privs` on a child, so set-user-ID binaries in the image stay an escalation path; and a non-root parent whose capabilities come from the ambient set passes them through `setuid` and `execve` to the CLI and every tool ([man] `capabilities(7)`: the sets are cleared only on a change from uid 0 to non-zero). Node cannot clear the ambient set of a child.
- An exec-only launcher keeps the process identity hudhud depends on. `execve` replaces the program in the calling process and keeps its pid ([man] `execve(2)`); `/proc/<pid>/stat` field 22, `starttime`, is set at fork and not reset by `execve` ([man] `proc(5)`). Both measured through `setpriv`: the same process showed pid 29, start time 33038493, process group 1 and session 1 before and after `exec setpriv <fixed flags> -- sh …`, only its credentials changed (probe §10.3). hudhud's identity is the spawned pid plus its start time (ADR-0011 J9, ADR-0010), so an identity read that lands before or after the launcher's `exec` records the same values. Measured (EXP-2 S7): the spawned pid was the CLI, `{"pid":5310,"uid":"10001","cliPid":5310}`, and `initialize.pid` equalled it, so no `binary.launcher-detected` diagnostic appeared.
- `setpriv` (util-linux) changes uid, gid and groups, sets `no_new_privs`, and clears the inheritable, ambient and bounding capability sets, then calls `execve`; it does not fork (`setpriv(1)`: "a simple, non-set-user-ID wrapper around execve(2)", probe §10.6; measured for 2.38.1 by EXP-2 S7 above and probe §10.3). With Docker's default root capabilities the fixed flag set of §2 produced exactly the credentials §4 requires (probe §10.1).
- Cross-uid signals need privilege: `kill(2)` succeeds only when the sender has `CAP_KILL` or its real or effective uid equals the target's real or saved uid ([man] `kill(2)`). hudhud maps `EPERM` from `kill` to `not-permitted` today (`packages/core/src/process/os/posix.ts`, `deliver`). With a root worker EXP-2's ladder worked across uids: S6 (`dispose` during `sleep 20`) ended `aborted` in 75 to 98 ms in every case, and S7's `SIGKILL` was `killed-externally`; no process of uid B was left in the container.
- Cross-uid `/proc` reads: `/proc/<pid>/stat` and `/proc/<pid>/status` are world-readable unless `/proc` is mounted with `hidepid` ([man] `proc(5)`); with `hidepid=1` hudhud counts the entries as `rejected`, with `hidepid=2` they are absent (ADR-0010 "Linux /proc hardening"). `/proc/<pid>/exe` and `environ` need a ptrace read check, which a worker without `CAP_SYS_PTRACE` fails for another uid ([man] `proc(5)`, `ptrace(2)`).
- macOS has no `setpriv`, no `/proc` and no Linux capability sets; Windows has no uids.

## Decision

### 1. API

A connect option, harness-namespaced and `@beta` (ADR-0003 tiers):

```ts
claudeCode: {
  spawnAs?: {
    uid: number;            // integer, not 0 / overflow / the host's euid
    gid: number;            // integer, not the host's egid or a supplementary group
    launcher: string;       // absolute path of util-linux setpriv, for example '/usr/bin/setpriv'
    launcherSha256?: string; // 64 hex; when set, the launcher's bytes must match
  };
}
```

- No default for `launcher`: the path is pinned by the application, never looked up in `PATH` (ADR-0011 §5 planting rules apply in full: absolute, `realpath`-resolved, a regular file).
- `uid` and `gid` must be integers in the range above. Refused (`rule` in parentheses): 0 (`spawn-as-range`: the agent as root defeats the purpose); 4294967295 (`spawn-as-range`: `setpriv --reuid=4294967295` exits 0 and leaves the uid unchanged, so the program runs as root, and `--regid=4294967295` leaves gid 0 — the `(uid_t)-1` "no change" value, measured, probe §10.4); the overflow ids from `/proc/sys/kernel/overflowuid` and `overflowgid`, read once (`spawn-as-overflow-id`: both `65534` on the probe host, probe §11.5, but read rather than assumed because they are tunable; a name-service lookup that fails returns the overflow id, so running as it usually means a misconfiguration); a `uid` equal to the host's own effective uid (`spawn-as-same-uid`: it would split nothing); and a `gid` equal to the host's effective gid or any of its supplementary groups (`spawn-as-same-gid`: B would share a group with the host and could reach the host's group-readable files).
- `launcher` must be absolute (`spawn-as-launcher-not-absolute`). Optional `launcherSha256` (64 hex): when set, the launcher's bytes are hashed and must equal it, so the trust does not rest on ownership alone (findings 2 and 10). `spawnAs` is otherwise `{ uid, gid, launcher, launcherSha256? }`; a bad shape is `spawn-as-shape`.
- Validation failures are `INVALID_OPTIONS` with `details.path` and `details.rule` (the rules named above).
- Platforms: Linux only. On Windows and macOS `connect()` fails with `CAPABILITY_UNSUPPORTED`, `details.capability: 'claudeCode.spawnAs'`, `details.reason: 'platform'` (`'win32'` or `'darwin'`). macOS is refused rather than emulated: there is no exec-only launcher with `no_new_privs` and capability clearing in the base system, and the post-spawn check of §4 has nothing to read without `/proc` (a macOS design is an open question, not part of 0.2.0).

### 2. How the CLI is started

hudhud still resolves and verifies the CLI exactly as today (`binaryPath` or discovery, digest table, strict mode; ADR-0011). `spawnAs` changes only what is executed:

```
<launcher> --reuid=+<uid> --regid=+<gid> --clear-groups --no-new-privs \
           --inh-caps=-all --ambient-caps=-all --bounding-set=-all -- <CLI realpath> <hudhud argv...>
```

- The flag set is fixed, built at the single argv point (ADR-0011 §3, `--flag=value` form), and cannot be extended by options or by `/raw` `extraArgs` (which only append to the CLI's own argv after `--`). `--ambient-caps=-all` is the one flag EXP-2 did not pass; it is added so that a non-root worker whose capabilities are ambient cannot leak them (Context). `setpriv` 2.38.1 accepts the exact combination with a root host and exits 0 with every capability set empty (probe §10.1), also under `no_new_privs` (probe §10.2).
- The ids are written with a leading `+` (`--reuid=+<uid>`), which forces `setpriv` to read them as numbers. A bare number is resolved through `getpwnam`/`getgrnam` first: with a decoy `/etc/passwd` line named `10001`, `--reuid=10001` ran as the decoy's uid 4000, while `--reuid=+10001` ran as 10001 (finding 2, probe §11.2). The post-spawn check of §4 would still catch the wrong uid, but the `+` form removes the name-service path entirely. hudhud confirms once per Harness that the launcher accepts `+` (the `setpriv --version` probe is also run with a `+`-form no-op to fail fast on an older `setpriv`); if it does not, `spawnAs` is refused (`rule: 'launcher-no-numeric-ids'`).
- `<CLI realpath>` is the file that was verified, not a name for the launcher to look up. The existing change check before spawn (`BinaryChangedError`, ADR-0011) applies unchanged.
- The `claude --version` probe of `connect()` (ADR-0011 K4) runs through the same launcher, so the CLI binary never executes with the host's privileges once `spawnAs` is set. Its working directory is still a fresh directory that hudhud creates and removes, created with mode `0711` instead of `0700` so that uid B can enter it but not list or write it (libuv enters the cwd as the parent, before `setpriv` runs, Q2 §2.1; the CLI then runs in it as B). Measured with stand-in programs: in a root-owned `0711` directory, a process switched to uid 10001 by the fixed flags could resolve the directory (`pwd`, `/bin/pwd -P`) and run `/bin/true`, and was refused listing and creating files (probe §10.5). That Claude Code's own `--version` works there is UNVERIFIED (no Claude binary was run).
- The CLI is still spawned non-detached; `setpriv` creates no session or process group, so the CLI stays in the host's process group, which hudhud never signals (ADR-0010). Measured: the process group and session of the exec'd process equal the caller's (probe §10.3), and `setpriv(1)` offers no option that would change them; EXP-2's dispose and sweep results are consistent with it. The source was not read.
- No `--pdeathsig` is used. `setpriv --pdeathsig=KILL` is accepted (exits 0) but does not fire: when the parent of a `setpriv … -- sleep` exited, the child stayed alive, reparented to pid 1 (finding 13, probe §11.6), because the credential change clears the pending parent-death signal. It would also be unreliable through Node regardless, since `PR_SET_PDEATHSIG` tracks the parent thread and libuv may spawn from a worker thread. Host death is handled as ADR-0010 and ADR-0008 already specify (the host-exit hook ends stdin; the CLI drains), not by a death signal.

### 3. Checks before spawn (at `connect()`, repeated at every session spawn)

Each failure is `SPAWN_AS_REFUSED` (new code, `retryable: false`) with `details.rule` and the offending path (paths are allowed in error details, as for `CWD_INVALID`; they never enter the posture). Nothing is spawned when a check fails.

1. Launcher provenance (`rule: 'launcher-unsafe'`): the launcher's `realpath` and every directory from it up to `/` must be owned by uid 0 and have neither the group-write nor the other-write bit (`mode & 0o022 === 0`); a symlink on the way is resolved and the same rule applies to the link's own directory chain. A file that uid B or the host's own (non-root) uid could replace is refused. When `launcherSha256` is set, the launcher's bytes must also match it (`rule: 'launcher-digest'`): ownership proves who can replace the file, the digest proves which file it is.
2. The runtime trust chain of `setpriv` (`rule: 'launcher-chain-writable'`): as root, `setpriv` also loads `ld-linux`, `libcap-ng`, `libc`, the `ld.so` cache and `/etc/ld.so.preload`, and resolving `--reuid` through a bare number would read `nsswitch.conf`, the NSS modules and `passwd` (finding 2; the `+` form of §2 removes the lookup, but the loader files remain). None of `/etc`, `/lib`, `/lib64`, `/usr` or the directories on the `ld.so` search path may be writable by B (owner, group or other, evaluated as in check 3). A read-only rootfs satisfies this; hudhud reports `spawn-as.rootfs: 'read-only' | 'writable-paths-checked'` from `/proc/self/mountinfo`. This is why `launcherSha256` alone is not enough: the digest pins the launcher, not the libraries it loads.
3. Launcher identity (`rule: 'launcher-not-setpriv'`): hudhud runs `<launcher> --version` once per Harness, as the host, with a minimal fixed environment (finding 1: only `PATH=/usr/bin:/bin`, no inherited `LD_*`, `GCONV_PATH`, `LOCPATH`, `GLIBC_TUNABLES` or other loader or libc variable), the same spawn hygiene as the CLI probe, and requires the output to start with `setpriv from util-linux `. The banner only tells hudhud it is probably the right tool; it is forgeable, so it is not a security control — the proof that the launcher is genuine is check 1 (root-owned, not writable by B) plus the optional `launcherSha256`, and the proof that it did its job is the post-spawn table of §4. A version older than the tested 2.38.1 is reported as `spawn-as.launcher-untested`, not refused.
4. CLI not writable by B (`rule: 'cli-writable-by-target'`): the CLI's `realpath` and every directory up to `/` must not be writable by (uid, gid): not owned by `uid`, not group-writable with group `gid`, not other-writable. `setpriv --clear-groups` leaves B with no supplementary groups, so `gid` is B's only group. A file B could rewrite would turn the next session's verified binary into B's code (TOCTOU, Q2 §2.2).
5. CLI and cwd reachable by B, and the cwd reachable by the host (`rule: 'not-reachable-by-target'` / `'cwd-unreachable-by-host'`): every directory from `/` to the CLI must be searchable by (uid, gid), the CLI executable by them, and the cwd and its ancestors searchable and the cwd readable by (uid, gid). Also, the host must itself be able to `chdir` into the cwd: libuv enters the cwd as the host before `setpriv` switches uid (Q2 §2.1), so a B-owned `0700` cwd that the host (without `CAP_DAC_OVERRIDE`) cannot enter makes the spawn fail (partner's extra ask for finding 4). hudhud evaluates both from mode bits and ownership, because `access(2)` tests only the host's uid; POSIX ACLs and LSM policy are not evaluated (a false "reachable" then ends as `SPAWN_FAILED` or a failing handshake, never as a weaker session).
6. Loader and libc environment (`rule: 'spawn-as-loader-env'`): `setpriv` is not set-user-ID, so its root child runs with `AT_SECURE` 0 and glibc honours the unsecure environment — measured, `LD_PRELOAD`, `LD_AUDIT` and `LD_LIBRARY_PATH` were all acted on (finding 1, probe §11.1). Under `spawnAs` the `'inherit'` preset is refused (`CAPABILITY_UNSUPPORTED` would hide the weakening; this is `INVALID_OPTIONS`, `rule: 'spawn-as-inherit'`), and the final child environment, however it was built, may not contain any `LD_*` name or `GCONV_PATH`, `LOCPATH`, `GLIBC_TUNABLES`, `RESOLV_*`, `RES_OPTIONS`, `HOSTALIASES`, `NIS_PATH`, `LOCALDOMAIN` or `TMPDIR`-via-loader names — the glibc `UNSECURE_ENVVARS` set — nor `NODE_OPTIONS` (already pinned-out, ADR-0012 §4). The application may still set `LANG` and `LC_*`. The `setpriv --version` probe (check 3) runs with the minimal fixed environment named there, so a loader variable in the host's own environment cannot subvert the probe either.
7. Child environment (`rule: 'spawn-as-env'`): the host's per-user variables are not passed to B. Under `spawnAs` both presets drop `HOME`, `USER`, `LOGNAME`, `TMPDIR`, `MAIL` and every `XDG_*` variable of the parent (reported in `env.dropped`), and the application must set `HOME` and `TMPDIR` itself (`env.add` or an explicit map), or the session is refused. A shared `TMPDIR` or `XDG_RUNTIME_DIR` would put B's sockets and task output in the host's directories (the CLI writes `$TMPDIR/claude-<uid>/…` and `cc-socks/<pid>.sock` there, EXP-2 §3; ADR-0010 "Sockets"). Whether those directories are owned by B, and the rest of the layout, is the job of the layout check ([ADR-0020](0020-layout-check.md)), which `spawnAs` turns on by default (`'enforce'` for the integrity codes, `'warn'` for the usability codes; ADR-0020 §1).
8. Inheritable file descriptors (`rule: 'fd-inheritable'`): hudhud reads `/proc/self/fdinfo/<n>` for every open fd ≥ 3 and refuses if any lacks `O_CLOEXEC` (the `flags` field without the `02000000` bit). Node opens its own fds `O_CLOEXEC` (measured: `openSync` gave `flags 02100000`, and a `spawn` child did not inherit the fd, finding 3, probe §11.3), so this never fires for a plain Node host; it catches an fd opened without `O_CLOEXEC` by a native addon or inherited into the host from its own parent, which would otherwise reach the CLI and its tools as uid B.
9. Host able to switch (`rule: 'host-cannot-switch-uid'` / `'host-ambient-nonempty'`): read once from `/proc/self/status`. If the host's effective uid is 0, `CapPrm ∩ CapBnd` must contain `CAP_SETUID`, `CAP_SETGID` and `CAP_SETPCAP` — the permitted set, not only the bounding set, because under `no_new_privs` `execve` grants a root process at most its prior permitted set (finding 7; confirmed, probe §11.5: a root host under NNP with `CapPrm` lacking `SETPCAP` ran `setpriv` to exit 0 but left the bounding set in place, `CapBnd 00000000000000e0`). For a non-root host, `CapAmb` must contain the three, since only ambient capabilities survive the host's own `execve` of `setpriv` ([man] `capabilities(7)`); and the host's `CapAmb` must then be exactly those (and `CAP_KILL` if wanted) with nothing else, because any extra ambient capability would reach the CLI (`rule: 'host-ambient-nonempty'`, finding 8). `CAP_SETPCAP` is needed for `--bounding-set=-all`, and `setpriv` does not fail without it (exit 0, bounding set unchanged, contrary to its man page's NOTES; probe §10.2); without `CAP_SETUID`, or as a non-root host with no capabilities, `setpriv` exits 127 (`setresuid failed`). The minimal root set `CAP_SETUID`, `CAP_SETGID`, `CAP_SETPCAP` plus `CAP_KILL` is enough, with or without `no_new_privs` (probe §10.2, §11.5). This check fails early with a clear rule; §4 is what guarantees the outcome.
10. `/proc` visibility (`rule: 'proc-hidden'`): the host must be able to read `/proc/<pid>/status` of uid B's processes. With `hidepid=1` or `hidepid=2` and the host neither root with `CAP_SYS_PTRACE` nor in the mount's `gid=` group, it cannot, and §4 and every snapshot would fail; hudhud refuses instead of running blind. Determined from `/proc/self/mountinfo` (the `hidepid` and `gid` mount options of the `/proc` mount) and the host's capabilities and groups. Under gVisor there is no `hidepid` (Q2 §2.3, from gVisor's source on 2026-10-18).
11. Controlling tty (`rule: 'spawn-as-tty'`): the host's own `tty_nr` (stat field 7) must be 0, because the non-detached child inherits the host's controlling terminal. A shared controlling tty would let a uid-B process push input to it with the `TIOCSTI` ioctl on kernels before 6.2 (where `TIOCSTI` needed only write access to the tty), and hudhud cannot know the kernel version portably, so it refuses rather than warns. Measured: a container without a pseudo-terminal gives `tty_nr` 0 for the host and the child (probe §11.5), so the normal sandbox passes; a host that allocated a tty (`docker -t`, a login shell) is refused, and the application drops the tty (run the host without one, or `setsid`).

### 4. Verification after spawn (fail closed)

The spawned process is `setpriv` until it calls `execve`, and the check must run on the CLI, not on `setpriv`, and before hudhud writes anything at all to the child — including the `initialize` request (partner finding 4; writing `initialize` first would hand bytes to a process whose credentials are not yet verified). So hudhud does not wait for the first stdout byte. It polls `/proc/<pid>/status` in bounded steps (about 1 ms, capped at the handshake's `firstFrameTimeoutMs`) until the `exec` is observed — `Name` (or `/proc/<pid>/cmdline`) is the CLI, not `setpriv` — and brackets the read with the start-time identity check (`/proc/<pid>/stat` field 22 equals the value recorded at spawn, before and after), so the read cannot land on a reused pid. Only once the status passes does hudhud write `initialize`. If the `exec` is not observed within the cap, the session fails `SPAWN_AS_FAILED` (`rule: 'exec-not-observed'`).

| Field | Required |
|---|---|
| `Uid:` (real, effective, saved, filesystem) | all four equal `uid` |
| `Gid:` (real, effective, saved, filesystem) | all four equal `gid` |
| `Groups:` | empty (the line is `Groups:` then a tab and, as measured, a trailing space before the newline, probe §11.4; the parser trims trailing whitespace and accepts it) |
| `CapEff`, `CapPrm`, `CapAmb` | `0000000000000000` |
| `CapInh`, `CapBnd` | `0000000000000000` (what the fixed flags set; a launcher that does not honour them — the silent `CAP_SETPCAP` skip of §3 check 9 among them — is caught here) |
| `NoNewPrivs` | `1` |
| `TracerPid` | `0` (no debugger is attached to the CLI; measured 0, probe §11.4) |
| `Seccomp`, `Seccomp_filters` | recorded in the diagnostic, not enforced (they reflect the container's own seccomp, not hudhud's; measured `2`/`2`, probe §11.4) |

hudhud also records `/proc/<pid>/limits` in the `spawn-as.verified` diagnostic (data only, not checked), so a host can see the resource limits the CLI ran under.

When `initialize` answers, `initialize.pid` must equal the spawned pid. This is a second layer and a misconfiguration guard (it catches a forking launcher, `rule: 'launcher-forked'`), not a security proof: after the `exec`, a uid-B process can already forge stdout by writing to `/proc/<cli>/fd/1` (§8), so `initialize.pid` matching does not prove the frames are the CLI's. The credential proof is the status table above, read before any byte is written.

When `/proc/<pid>/exe` is readable (host is root with `CAP_SYS_PTRACE`), its device and inode must equal the verified CLI's; when it is not readable (`EACCES`), this sub-check is reported as `unverifiable` in the session's `spawn-as.verified` diagnostic, never silently passed.

Any mismatch, or a status that cannot be read: the session fails with `SPAWN_AS_FAILED` (new code, `retryable: false`, `details.rule` one of `uid-mismatch`, `gid-mismatch`, `groups-not-cleared`, `capabilities-not-cleared`, `no-new-privs-off`, `tracer-attached`, `launcher-forked`, `exec-not-observed`, `exe-mismatch`, `status-unreadable`, with the observed field names, not values beyond the numbers above). hudhud then ends the process at once: stdin is closed (EOF) and the abort ladder of ADR-0010 runs. Because no user message was written, no tool has run on the agent's behalf. Residual, documented: the CLI's own start-up (user-scope hooks such as `SessionStart`, user-scope MCP servers) may already have started processes with the faulty credentials before the `exec` was observed; in the recommended layout those come from root-owned configuration ([ADR-0020](0020-layout-check.md)), not from the agent. Without `CAP_KILL` the ladder can only close stdin (§6); the failure says so in `details.terminated: false`.

Success emits the diagnostic `spawn-as.verified` (`data`: `uid`, `gid`, `noNewPrivs`, `tracerPid`, `seccomp`, `exe: 'verified' | 'unverifiable'`, `limits`).

### 5. gVisor (unverified until a fixture exists)

Every probe above ran on a native Linux kernel in Docker. Under gVisor (runsc) the `/proc` fields and `prctl` behaviour `spawnAs` depends on are reimplemented by the sentry and are not verified. `spawnAs` is therefore **not acceptable to ship** until a gVisor fixture of the §4 status read exists (the partner will record one from the §10.1 probe). Per field, the plan is:

| Dependency | If the gVisor fixture confirms it | If it does not |
|---|---|---|
| `/proc/<pid>/status` `Uid`, `Gid`, `Groups`, `Cap*`, `NoNewPrivs`, `TracerPid` present and correct after a uid switch | use as on native Linux | `spawnAs` reports `CAPABILITY_UNSUPPORTED` on gVisor (a runtime probe at `connect()` detects the sentry) |
| `/proc/<pid>/stat` field 22 (`starttime`) stable across `exec` | identity and the §4 bracket work | fall back to `/proc/<pid>/status` `Name`-plus-parent identity, or unsupported |
| `prctl(PR_SET_NO_NEW_PRIVS)` honoured by `setpriv` | NNP enforced | unsupported (the setuid-binary escalation path is open) |
| `/proc/self/mountinfo` reporting `hidepid` (there is none in gVisor, Q2 §2.3) | check 10 passes trivially | unchanged |

Until the fixture lands, the status line marks ADR-0019 not acceptable, and the gVisor lane (§9) is expected-fail. gVisor's `/proc/<pid>/fd` reopen behaviour (relevant to §8) is separately UNVERIFIED (Q2 §A.5).

### 6. Containment across uids

Whether the host may signal uid B is decided at `connect()` from the host's `CapEff` (`CAP_KILL`) and confirmed at run time by the first signal's result.

- With `CAP_KILL` (or as root with it in the effective set): ADR-0010 applies unchanged. Identity, snapshots S1 and S2, the EOF snapshot, `SIGTERM`, `SIGKILL`, the verified `kill(-pgid)` of tool groups and the sweep after the exit (R3-1) all work across uids, as EXP-2 S6 and S7 measured with a root worker. `processContainment` stays `'best-effort'`.
- Without `CAP_KILL`: `processContainment` is `'best-effort'` with `capabilities.reasons.processContainment: 'cross-uid-no-kill'`, the posture entry `spawnAs.signals: 'not-permitted'`, and a `containment.cross-uid-no-kill` diagnostic at session start. What hudhud can and cannot guarantee then, stated in the docs exactly so:
  - It can: send `interrupt`, close stdin, take the snapshots (`/proc` is readable, §3 check 10), and report every survivor by pid and start time.
  - It cannot: deliver `SIGTERM` or `SIGKILL` to the CLI or any tool, or sweep. The ladder's signal steps are recorded as `not-permitted` (not as failures of hudhud), the sweep after the exit reports `status: 'skipped'`, `reason: 'not-permitted'`, with `data.survivors` (the count of verified snapshot descendants still alive).
  - Consequences: a CLI that ignores EOF (a wedged CLI, or one finishing a long tool; measured, the CLI finishes its in-flight tool before exiting on EOF, ADR-0010) keeps running; `dispose()` still resolves after the ladder's bounded waits, with `session.terminated` `outcome` from the existing classification and the `termination.ladder` diagnostic showing the skipped steps. Descendants that survive the CLI (a daemon started with `setsid`, the `rg --files` child of the drain-path finding) stay alive until the application tears the sandbox down. The application must own that teardown; hudhud cannot.
- The sweep's protected set is unchanged: the host's group, pid 0 and 1, the spawned pid and the signal target's group are never signalled. The after-exit walk's rules (R2-1: a parent's pid names that parent only while it provably held it) do not depend on the uid and are unchanged; under `hidepid` the session never starts (§3 check 10), so the walk never runs on a partial table.
- A uid-B process cannot signal the host ([man] `kill(2)`): the host's own exit hook (ADR-0008) and ladder timers cannot be disturbed by B's signals. B can still close or flood its own pipes; the framer bounds (ADR-0011 §7) apply as before.

### 7. Posture and diagnostics

- Posture entries (connect): `claudeCode.spawnAs` with value `'uid-split'` or `'off'` (default `'off'`; numbers are not secrets but the posture lists kinds, so `uid` and `gid` appear in the `spawn-as.verified` diagnostic instead), and `spawnAs.signals`: `'permitted' | 'not-permitted'` when set. `spawnAs` strengthens a default, so it is not a `dangerously*` option; it is listed because every security-relevant setting is (ADR-0012 §7).
- Diagnostics: `spawn-as.verified`, `spawn-as.launcher-untested`, `containment.cross-uid-no-kill`; the existing `env.dropped` names the per-user variables of §3 check 7.

### 8. Threat model statement (amends ADR-0012's threat model when accepted)

What the split protects: the host process's memory, environment, signals and files (mode `0600` or `0700` and owned by the host's uid), and with them the host's channel to its control plane. What it does not protect: anything the CLI itself holds. The CLI and its tools share uid B, so a tool can read the CLI's environment (including the API credential or gateway token that the CLI needs) and, for a dumpable CLI, reopen its pipes through `/proc/<cli>/fd` and inject frames towards hudhud (Q2 §A.5; the reopen is UNVERIFIED, not run in EXP-2). hudhud already treats every frame from the CLI as untrusted (ADR-0012 §8); applications must not treat the in-sandbox event stream as audit after a compromise. `spawnAs` does not replace session-scoped credentials and authorization outside the sandbox (Q2 §2.4 (c)).

### 9. Tests

- Unit (all OSes):
  - option validation: shape, ranges, `0`, `4294967295`, same uid, relative launcher, Windows and macOS refusal with `CAPABILITY_UNSUPPORTED`;
  - the launcher argv: the exact fixed flag list, `--flag=value` form, `--` before the CLI path, `/raw` `extraArgs` only after the CLI path;
  - the `/proc/<pid>/status` parser on fixture files (Linux 5.x and 6.x layouts, the gVisor layout once recorded), including missing fields (refused), hex masks with leading zeros, the `Groups:` line with a trailing space (probe §11.4), and `TracerPid` non-zero (refused);
  - the mode-bit evaluator for checks 1, 2, 4 and 5, against a reference oracle, including the host-reach-cwd case (a B-owned `0700` cwd, host without `CAP_DAC_OVERRIDE`);
  - the environment rules of check 6: `'inherit'` refused under `spawnAs`; every `LD_*` and glibc unsecure name refused in the final child environment; `LANG`/`LC_*` allowed;
  - the id rules: `0`, overflow id, host euid, host egid and supplementary gid refused; the `+`-prefixed argv form;
  - the fd scan of check 8 against a fdinfo fixture with and without the `O_CLOEXEC` bit;
  - the posture entries, diagnostic shapes, and the two new error codes in the code table and `errors.schema.json` (`retryable: false`).
- Property (fast-check): the mode-bit evaluator against the oracle over arbitrary (owner, group, mode, sticky, uid, gid) chains; the status parser never accepts a status whose `Uid:`, `Gid:` or capability fields differ from the requirement; the argv builder never lets an option value appear before `--`.
- Conformance (sans-IO, loopback): the termination ladder and the sweep after the exit with every signal answering `not-permitted` (the step records, `status: 'skipped'`, `reason: 'not-permitted'`, `survivors`); `SPAWN_AS_FAILED` before any user message is written (the recorded stdin holds the `initialize` request only).
- Integration, uid-split Docker lane (Linux, `node:22` and `node:26` images, ADR-0013 hygiene: mock API, CONNECT trap, pinned hash-verified CLI; local runs take the shared Docker lock). Base container: `--user 0 --cap-drop ALL --cap-add SETUID --cap-add SETGID --cap-add SETPCAP --cap-add KILL --init`, the CLI and `setpriv` root-owned, a per-uid `HOME` and `TMPDIR` laid out as [ADR-0020](0020-layout-check.md) recommends.
  - Must pass: text turn, Bash turn, resume, fork; `spawn-as.verified`; a Bash tool's `cat /proc/<host pid>/environ` fails with `EACCES` and its `kill <host pid>` fails with `EPERM`; `dispose()` during `sleep 20` ends `aborted`; a `setsid` daemon started by a tool is killed by the sweep after the exit; no uid-B process is left.
  - Variant without `--cap-add KILL`: `cross-uid-no-kill` in capabilities, posture and diagnostics; the ladder's signal steps are `not-permitted`; the sweep reports the daemon as a survivor and does not kill it; `dispose()` resolves within its bounds.
  - Variant with `--security-opt no-new-privileges` on the container: must pass as the base (`setpriv` itself was measured to work there, probe §10.2; the lane confirms it with the CLI).
  - Variant `--cap-drop SETPCAP` with the check of §3 check 9 disabled by a test seam: `setpriv` exits 0 with the bounding set left in place (probe §10.2), and §4 must fail the session with `capabilities-not-cleared`.
  - Must refuse, each asserting that no process of uid B ever ran (a process-table check before and after): a launcher that is group- or other-writable; a launcher in a directory that uid B owns; a launcher not owned by root; a non-`setpriv` launcher (`launcher-not-setpriv`); a CLI file owned by uid B (`cli-writable-by-target`); a container started as a non-root user without capabilities (`--user 1000 --cap-drop ALL`: `host-cannot-switch-uid`, the setuid-less environment); `HOME` or `TMPDIR` not set by the application (`spawn-as-env`).
  - Must fail after spawn, each through a root-owned test launcher that prints the `setpriv` version line and then misbehaves: keeps an ambient capability (`setpriv … --inh-caps=+kill --ambient-caps=+kill`: `capabilities-not-cleared`); switches to `uid + 1` (`uid-mismatch`); omits `--clear-groups` with the host in a supplementary group (`groups-not-cleared`); forks and waits instead of exec (`launcher-forked`). Each asserts that stdin received only `initialize` and that the CLI was ended.
  - Variant with a decoy `/etc/passwd` entry named for the uid (`10001:x:4000:…`): the session still runs as the configured uid, because the argv uses the `+` numeric form (probe §11.2); a test seam that drops the `+` must be caught by `uid-mismatch` in §4.
  - Variant with an `LD_PRELOAD` of a marker library set in the host environment: the marker must not appear (check 6 refuses it before spawn); and a direct `setpriv`-with-`LD_PRELOAD` control proves the marker would otherwise load (probe §11.1).
  - Variant with a controlling tty (`docker -t`): `spawn-as-tty` refusal.
  - Variant with a writable `/etc` or `/usr` (a `tmpfs` mount): `launcher-chain-writable` refusal.
  - Optional variant: `/proc` remounted `hidepid=2` (needs `CAP_SYS_ADMIN` in the setup step only): `proc-hidden` refusal; and `hidepid=2,gid=<host group>` with the host in that group: must pass.
  - gVisor lane (`--runtime=runsc`): expected-fail until the gVisor status fixture (§5) lands, then a parity run of the must-pass cases.
- The Windows and macOS jobs run the unit refusal tests only; no real-CLI test exists there for `spawnAs`.
- CI tier (ADR-0014): the lane runs on FULL in the Linux job (it is a container step, about the cost of one more integration project; to be measured and sized by K15 before adoption) and in the nightly canary against the newest CLI.

## Alternatives considered

- Node's `spawn({ uid, gid })` (Q2 option (a)). Not chosen for 0.2.0 (partner's answer to our open question, adopted): it keeps the host's bounding and inheritable capability sets instead of clearing them, it cannot set `no_new_privs` on the child (so set-user-ID binaries in the image stay an escalation path), and libuv calls `setgroups(0, NULL)` and ignores a failure, so a host without `CAP_SETGID` leaves the child in the host's supplementary groups (Q2 §2.1, §A.2). It would be safe only for a uid-0 host with `CapAmb` 0 and `no_new_privs` set container-wide; offering it as a second way is an open question.
- `setpriv --pdeathsig=KILL` in the fixed argv. Rejected on evidence (finding 13): it is accepted but does not fire — a `setpriv … -- sleep` child outlived its parent, reparented to pid 1 (probe §11.6), because the credential change clears the pending signal; and it tracks the parent thread, which libuv may not keep. Host death is handled by the exit hook and drain of ADR-0008 and ADR-0010.
- `--securebits` (for example `noroot`) in the fixed argv. Not added: the fixed flags already clear every capability set and set `no_new_privs`, so a root child of `setpriv` gains nothing at a later `execve` to lock down; `securebits` would add surface (the `keep_caps` interactions, `_locked` variants) without changing the measured outcome (`CapEff`/`CapPrm`/`CapAmb` already 0, probe §10.1). Left out deliberately.
- Any launcher, as an application-supplied `claudeCode.launcher: { path, args }` (Q2 option (b) general form). Not chosen for 0.2.0: hudhud could not state what the launcher did, and the post-spawn requirements of §4 would have to be configurable. Pinning `setpriv` with a fixed flag set makes every guarantee checkable. A general launcher seam (for `bwrap`, `nsenter`, a delegated-cgroup launcher) stays a roadmap item.
- `sudo`, `su`, `runuser`. Rejected: they fork (`sudo` keeps a monitor parent by default; `su` and `runuser` open PAM sessions), so the spawned pid is not the CLI; the identity would be the launcher's, and signals cross-uid fail anyway (Q2 §A.1).
- A `#!` wrapper script as `binaryPath` that execs `setpriv` (works today, ADR-0011 J9). Not the supported way: hudhud verifies the script, not the CLI (EXP-2 reported `binary.unverified` for exactly this reason), and nothing checks the resulting credentials.
- Refusing `spawnAs` without `CAP_KILL`. Not chosen: in a per-session disposable sandbox, teardown is the boundary, and interrupt plus EOF end a healthy CLI; hudhud reports the gap instead (§6).
- The saved-uid trick (leave the host's uid as B's saved uid so it can signal B without `CAP_KILL`). Rejected: `execve` copies the effective uid to the saved set-user-ID ([man] `execve(2)`), and a saved uid of A would let B switch back to A (Q2 §2.2).
- `pidfd_send_signal`. Rejected for permission: it applies the same checks as `kill(2)` ([man] `pidfd_send_signal(2)`); it solves pid reuse, not privilege.
- Requiring `hidepid`. Rejected: it buys nothing for the host's secrets that the uid split does not already give (environ and mem need the ptrace check either way) and costs hudhud its identity unless the host is in the `gid=` group (Q2 §A.4).

## Consequences

- Two new error codes (`SPAWN_AS_REFUSED`, `SPAWN_AS_FAILED`), additive to the closed code list and to `errors.schema.json`; consumers with a `default:` branch are unaffected (ADR-0005).
- A session with `spawnAs` starts later by one `/proc` read and, per Harness, one `setpriv --version` run.
- The application must provide the uid, gid, launcher, a per-uid `HOME` and `TMPDIR`, and a configuration layout B cannot write; [ADR-0020](0020-layout-check.md) reports what it gets wrong.
- Without `CAP_KILL`, hudhud's dispose guarantees shrink to what §6 lists, and the docs and the posture say so.
- hudhud's own read-only scans (the user `settings.json` for `managedPolicy`, the project credential guard, ADR-0012) still run as the host. A non-root host cannot read files that B owns with mode `0600`; the existing fail-safe values apply (`'unknown-user-settings-unreadable'`, a refusing guard). In the recommended layout the configuration is root-owned and world-readable, so this does not arise.
- Acceptance conditions: the gVisor status fixture of §5 recorded, and the uid-split lane green on FULL, including the `no-new-privileges`, the decoy-passwd, the `LD_PRELOAD`, the writable-chain and the forking-launcher variants.
