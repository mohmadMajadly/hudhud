# Troubleshooting

Every failure hudhud raises is a `HudhudError` subclass with:

- `code`: one of the stable codes below (also `HUDHUD_ERROR_CODES`);
- `retryable`: `true` when repeating the same call with the same inputs may succeed without any change by the application;
- `details`: JSON with the specifics; names of variables and files, never their values;
- `name`: the class name (`AbortError` for `ABORTED`).

Check codes with `isHudhudError(error, code)` rather than `instanceof`. A turn that ends with an error (for example `max-turns`, or an API error the CLI reported) is not an exception: it is a `TurnResult` with `isError: true` ([Sessions](sessions.md#ask-and-send)).

```ts
/** Runs `operation` again while it fails with a retryable error, up to `attempts` times. */
async function withRetry<T>(operation: () => Promise<T>, attempts = 3): Promise<T> {
  for (let attempt = 1; ; attempt += 1) {
    try {
      return await operation();
    } catch (error) {
      if (!isHudhudError(error) || !error.retryable || attempt >= attempts) throw error;
      console.warn(`attempt ${String(attempt)} failed with ${error.code}; retrying`);
    }
  }
}
```

Where errors surface:

| Phase                                             | Surface                                                                             |
| ------------------------------------------------- | ----------------------------------------------------------------------------------- |
| Options, binary, working directory, project guard | `connect`, `create` or `resume` rejects; nothing was started                        |
| Start and handshake                               | `create` or `resume` rejects after the process was stopped; nothing is left running |
| A turn                                            | `ask` and `turn.done` reject only for failures of the whole session                 |
| After the session ended                           | Every call rejects with the error that ended it, or `SESSION_CLOSED`                |

## Common situations

**`connect()` works in a terminal but not in a service.** Services often run with another user, `PATH` and home directory. hudhud looks in the service user's `~/.local/bin` and `PATH`; pass `binaryPath`. Claude Code's login also belongs to that user: sign in as that user, provide `ANTHROPIC_API_KEY`, or use `claudeCode.configDir`.

**A tool cannot find a variable it needs.** The default environment is an allowlist. Look at the `env.dropped` diagnostic and add what the tool needs with `env: { preset: 'harness', add: { ... } }` ([The environment](security.md#the-environment)).

**The session hangs on a tool.** Look for `stalled` events and their `pendingPermissions`: with `onPermission`, an unanswered question blocks Claude Code, and hudhud never times it out for you.

**`ask()` resolved, but `isError` is `true`.** That is a turn result, not a hudhud failure. Look at `outcome`, `errors`, `apiErrorStatus` and `raw`.

**Mutating tools are always denied.** In `default` mode without `onPermission`, Claude Code denies tools that change something. Pass `onPermission`, allow the tool with `claudeCode.allowedTools`, or choose another permission mode ([Permissions](permissions.md)).

**A `settings-guard.git-root-unresolved` diagnostic.** The project credential guard could not find the repository root from `.git` (`data.reason`: a symlinked or unreadable `.git`, a malformed `.git` file, an unreadable `gitdir` or `commondir`, a link to another host), so it checked the settings of the working directory and of every ancestor directory instead. The session runs; the guard was stricter, not weaker. To remove the diagnostic, repair what `data.reason` names for `data.path`, or start the session in a plain checkout ([Security](security.md#the-project-credential-guard)).

**A `settings-guard.symlink-followed` diagnostic.** A project settings file is a link (`data.path`); the guard checked the file it leads to (`data.target`), as Claude Code reads it. Nothing to fix if the link is yours; a link that dangles or leads to another host fails the start with `PROJECT_CREDENTIAL_ENV` instead.

**The termination diagnostics show `no-identity` (Linux).** hudhud could not read Claude Code's identity safely, so it ended only the process it spawned and recorded and swept no descendant. Inside a pid namespace whose `/proc` belongs to the parent namespace (`unshare -p -f` without `--mount-proc`) hudhud refuses the process table on purpose (internal code `EPIDNS`): each pid there names another process. Mount a `/proc` of your namespace (`--mount-proc`, or a container's own) ([Diagnostics](diagnostics.md#end-of-a-session), [Platforms](platforms.md#process-containment)).

**A snapshot step shows `rejected-<n>`.** `n` entries of the process table could not be read or parsed, typically other users' processes under `/proc` mounted `hidepid=1` (Linux). hudhud never signals such a process, and under `hidepid=1` it cannot be one of Claude Code's descendants; no action is needed.

**`compat.status` is `'untested'`.** The installed Claude Code is newer or older than the tested window. It runs; watch for `PROTOCOL_ERROR` and new `harness.frame` events, and prefer the tested version in production ([Compatibility](compatibility.md)).
